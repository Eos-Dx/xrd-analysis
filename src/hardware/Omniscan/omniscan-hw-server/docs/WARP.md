# WARP.md

This file provides guidance to WARP (warp.dev) when working with code in this repository.

## Common commands

Prereqs: Rust toolchain (MSVC on Windows), and protoc (Protocol Buffers compiler) in PATH.

- Build
  ```bash path=null start=null
  cargo build
  cargo build --release
  ```
- Run (server; plaintext by default)
  ```bash path=null start=null
  cargo run -- --config config/server.toml --grpc-addr "[::1]:50051"
  ```
- Run with GUI demo (feature is enabled by default; or run the GUI-only binary)
  ```bash path=null start=null
  cargo run -- --config config/server.toml         # will launch GUI if config.device.gui_mode = true
  cargo run --bin gpio-gui --features gui          # direct GUI demo binary
  ```
- Disable default features (e.g., headless server)
  ```bash path=null start=null
  cargo run --no-default-features --features tls -- --config config/server.toml
  ```
- Lint/format
  ```bash path=null start=null
  cargo fmt
  cargo clippy -D warnings
  cargo check
  ```
- Tests
  ```bash path=null start=null
  cargo test                              # all tests
  cargo test -- --nocapture               # show test output
  cargo test safety                       # filter by module/name
  cargo test --test workflow_integration_tests   # a single integration test target
  ```
- Security/documentation (optional tools)
  ```bash path=null start=null
  cargo install cargo-audit --locked      # once
  cargo audit
  cargo doc --open
  ```
- Quick gRPC probes (dev/plaintext)
  ```bash path=null start=null
  grpcurl -plaintext localhost:50051 hub.v1.Health/Liveness
  grpcurl -plaintext localhost:50051 hub.v1.Acquisition/GetState
  grpcurl -plaintext localhost:50051 hub.v1.Safety/GetInterlockStatus
  ```

Notes
- Protobuf stubs are generated by build.rs via tonic-build on cargo build; no manual step required.
- On Windows, install protoc via Chocolatey: `choco install protoc`.

## High-level architecture

- Entrypoint and runtime
  - `src/main.rs` loads `config/server.toml`, initializes tracing/logging, constructs demo devices (GPIO/Detector/Motion/PDU), creates a Tokio runtime, and starts the gRPC server via `run_grpc_server(...)`.
  - GUI integration (feature `gui`): when `config.device.gui_mode` is true, the GUI runs on the main thread and the gRPC server runs in a background Tokio runtime; otherwise the server runs normally without GUI.
  - A `tokio::sync::broadcast::channel` is created early and injected into GPIO and service state to publish `StateChangeNotification` events.

- gRPC layer
  - Protos: `proto/hub/v1/hub.proto` (Acquisition, Motion, DeviceControl, Safety, Health, StateMonitor, DeviceInitialization).
  - Codegen: `build.rs` uses `tonic_build` to generate modules included in `src/grpc/mod.rs` via `tonic::include_proto!("hub.v1")`.
  - Service implementations live in `src/grpc/services.rs` (plus `state_monitor_service.rs`). All services operate over a shared `ServiceState` holding:
    - `SafetyStateMachine`, device trait objects (Detector/Motion/GPIO), `AuditLogger`, optional `device_uuid` (for mTLS), and the broadcast sender.
  - Eventing: `ServiceState::notify_state_change(...)` broadcasts lightweight notifications; long-lived streaming APIs are scaffolded (e.g., `SubscribeRunEvents`) and can be filled in later.

- Safety-critical core
  - `src/safety/mod.rs` defines the FDA-oriented `SafetyStateMachine` with states: LOCKED, INITIALIZED, IDLE, WARMING_UP, CALIBRATED, PENDING_ARMED, RUNNING, STOPPING, SAFE, CALIBRATION, MAINTENANCE.
  - `InterlockStatus` aggregates key hardware conditions (key switch, enable button, E‑stop, door, beam watchdog, over-temp) and computes `overall_safe` with a `violation_reason`.
  - Key workflows:
    - Initialization evaluates interlocks and transitions to IDLE or SAFE.
    - `start_measurement(...)` enforces valid calibration and interlocks, requiring a physical enable (PENDING_ARMED → RUNNING) with timeout.
    - `stop/abort` drive SAFE/STOPPING transitions and audit logging.
  - Every transition is audit-logged (`CommandLog`) with before/after state and interlocks snapshot.

- Device abstraction layer
  - Traits under `src/devices/` define hardware interfaces:
    - Detectors (`detectors/`), Motions (`motions/` incl. `xy_demo.rs`), GPIO (`gpio/` incl. GUI/test/demo), and PDU (`pdu/`).
  - The server composes demo implementations by default; real drivers can replace them behind the same traits without touching service logic or safety code.

- Audit and compliance
  - `src/audit/` provides `AuditLogger` writing structured `CommandLog` entries (SQLite file under `config.logging.log_dir` in config).
  - gRPC services log each command with user context, timing, and results; the safety state machine logs all transitions.

- Configuration and logging
  - `ServerConfig` loads from TOML (`config/server.toml`) and drives behavior such as GUI mode, enable button timeout, logging directories, and certificate settings.
  - Tracing is set up via `src/logging.rs` with `tracing`/`tracing-subscriber` (JSON and env filter support).

- Security and certificates
  - TLS feature gates are present (default features include `tls` and `gui`). mTLS fields are parsed from config; certificate validation hooks exist in services but peer cert extraction is a stub under current `tonic` APIs. Development runs plaintext; production should enable mTLS when upgraded.

- Testing
  - Unit tests live alongside modules (e.g., `safety`), and integration tests live under `tests/` (notably `tests/workflow_integration_tests.rs`).
  - Tests cover calibration validity, warmup timing/status, LED transitions, and basic safety gating; use `-- --nocapture` to see logs.

- State monitoring
  - `StateMonitor` service exposes: a broadcast subscription for coarse-grained updates, and RPCs to fetch detailed `FullServerStateResponse`/device states. GPIO exposes key switch/enable states; Acquisition’s stream is scaffolded for future real-time events.
